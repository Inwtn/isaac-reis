Finance Sync API

A Java and Spring Boot integration service that turns incoming financial transactions into rows in Google Sheets. Instead of retyping cash-flow movements into a management spreadsheet, a connected system sends the transaction to a REST endpoint and the API records it in the configured sheet.

Java 17Spring Boot WebLombokGoogle Sheets API v4Google Auth LibraryMaven

The problem

Cash-flow controls often rely on spreadsheets that someone has to update by hand. Repeated data entry creates an operational bottleneck and increases the chance of inconsistent records. I built this project as an integration middleware: keep the spreadsheet used by the business, but automate how transaction data reaches it.

How a transaction travels through the system

  1. A client sends an HTTP POST request to /api/v1/transactions with the date, transaction type, category, description and amount in a JSON payload.
  2. The REST controller receives the request and maps it to a TransactionRequestDTO, keeping the incoming data contract separate from the integration code.
  3. GoogleSheetsService obtains service-account credentials with the Google Sheets scope and creates an authenticated Sheets API client.
  4. The service assembles the five transaction fields in a consistent column order and appends the row to the configured spreadsheet using the Sheets API.
  5. The controller returns an HTTP success response when the write completes, or an error response if the integration fails.

Architecture and implementation

The project separates responsibilities into Controller, Service and DTO layers. The controller handles the HTTP boundary; the service owns Google authentication and the external API call; the DTO represents the transaction received from the client. The spreadsheet ID is supplied through application configuration. The current implementation appends rows to the Página1 worksheet with the USER_ENTERED value option, so Sheets interprets values as it would during manual entry.

Key capabilities

  • Receive financial transactions over HTTP without requiring a person to open and edit the spreadsheet.
  • Record date, type, category, description and amount in a predictable structure for managerial cash-flow control.
  • Authenticate the integration through a Google service account with access to the destination spreadsheet.
  • Write each submitted transaction as its request is processed, connecting operational systems directly to a familiar reporting tool.

A practical example

A business system registers a software-license expense and submits its date, category, description and value. Finance Sync writes the corresponding row into Google Sheets. The finance team can then continue using that sheet for its controls without re-entering the same transaction.

Bank Reconciliation Engine

A reconciliation application that compares bank-statement transactions against financial entries already recorded in a system. It imports OFX or CSV statements, runs a matching process and separates reconciled transactions, statement discrepancies and internal entries that remain pending.

Java 17Spring Boot 3.2PostgreSQLSpring Data JPAHibernateREST APISwagger UIDocker

The problem

A bank statement and an internal cash-flow record describe the same financial activity from different sides. Comparing them manually is repetitive: someone must check amounts, debit or credit types, dates and missing entries. This project automates that comparison and makes the results available through a web dashboard and a documented REST API.

From statement upload to reconciliation report

  1. Upload an OFX or CSV statement. A parser reads its transactions, and an import record tracks the file and its processing status.
  2. For each bank transaction, the engine first looks for a pending internal entry with exactly the same amount, transaction type and date.
  3. If no exact-date match is found, it searches within a date tolerance. The current service uses ±1 day, defined in code, and chooses the candidate with the nearest date.
  4. A successful match links the bank transaction and the internal financial entry, marking both as reconciled.
  5. A statement transaction without a match is marked as divergent. Internal entries that have not been matched remain pending.
  6. The result includes categorized records, counts, monetary totals and the reconciled percentage, while the import history keeps the processing record available for review.

What the application includes

  • OFX and CSV statement ingestion, with dedicated parsers and an import-processing service.
  • Matching by amount, debit/credit type and date, with a fallback for nearby dates.
  • A dashboard for reviewing reconciliation results and a history of statement imports.
  • REST endpoints to create and list financial entries, filter pending entries, import statements and retrieve reconciliation history.
  • Interactive API documentation through Swagger UI and a PostgreSQL-backed persistence layer.

Architecture and data

Controllers expose the API; services coordinate statement processing and reconciliation; repositories persist financial entries, imported statement rows and import history. The model keeps both sides of a match linked, allowing a reconciled statement row to be traced to its internal entry. Spring Data JPA and Hibernate provide the database access layer. Docker Compose is included for running the application environment.

A practical example

An internal payable is recorded as a debit, but the bank posts the payment on the following day. If its amount and type match and the date is within the configured tolerance, the engine can reconcile the two records. A bank movement with no corresponding internal entry is surfaced as divergent; an internal bill absent from the statement stays pending for follow-up.
